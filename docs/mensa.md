## Mensa (eigene Bento-Kachel `#mensa-card`)

Eigenständige Kachel (`mensa` in `BENTO_TILE_META`, siehe „Bento-Grid-Layout", standardmäßig als letzte Zeile unter der Ranglisten-Kachel — sowohl im statischen HTML als auch in `bentoDefaultRows()`): zeigt den **heutigen** Speiseplan von vier Mensen (Harzmensa, Franckesche Stiftungen, Neuwerk, Tulpe) und bietet einen Check-in/Voting-Mechanismus, analog zum Bibliotheks-Check-in auf der Rennstrecke-Kachel, aber ohne Streckenbild/Hover-Polygone (reines Grid aus `.mc-tile`-Kacheln). Gleiche Sichtbarkeits-Bedingung wie Leaderboard/Rennstrecke (`setLeaderboardVisibility()`, um eine dritte Kachel erweitert).

### Externe Datenquelle

Die offizielle Studentenwerk-Halle-Seite (`studentenwerk-halle.de/mensen-cafebars/speiseplaene`) hat kein eigenes API — sie bettet ein Drittanbieter-iframe ein: `https://meine-mensa.de/speiseplan_iframe`. Datenfluss (per curl gegen die echte Seite verifiziert):
- `GET /speiseplan_iframe` liefert Session-Cookies (`XSRF-TOKEN`, `meine_mensade_session`) + CSRF-Token (`<meta name="csrf-token">` und Hidden-Input `_token`) — klassisches Laravel-Formular, kein JSON-API.
- `POST /speiseplan_iframe` (gleiche Cookies) mit `_token`, `date=<YYYY-MM-DD>`, `week=0`, `location_ids[]` (mehrfach, ein Wert pro gewünschter Mensa) liefert rohes, serverseitig gerendertes HTML mit allen angeforderten Speiseplänen in einem Request.
- **Ermittelte `location_ids`**: Harzmensa=3, Neuwerk=9, Tulpe=10, Franckesche Stiftungen=14.
- **DOM-Struktur**: Jede Mensa ist ein eigener `<div class="card mt-3">`-Block mit `<h5>Speiseplan <Name></h5>` im Header, gefolgt von `<div class="card food-container">`-Elementen (ein Div pro Gericht) mit `.food_title` (Name), `.prices` (`"3,40 / 6,30 / 8,40€"`, deutsches Komma-Dezimalformat, Studis/Mitarbeitende/Gäste), `img[data-toggle="tooltip"]`-Badges (`title`-Attribut = Diät-Hinweis) und einem `.collapse`-Div mit der rohen Zusatzstoffe/Allergene-Liste.
- **CORS**: der Server spiegelt jeden `Origin`-Header (+ `Access-Control-Allow-Credentials: true`) zurück — ein direkter Client-Fetch wäre technisch möglich gewesen, ist aber undokumentiertes Drittanbieter-Verhalten ohne jede Garantie (kann sich jederzeit ändern, keine SLA). Bewusste Entscheidung: **serverseitiger Scrape statt Live-Client-Fetch** — vermeidet außerdem, dass jeder Seitenaufruf jedes Nutzers live gegen das fremde Produktivsystem läuft.

### Scrape-Mechanismus

`supabase/functions/scrape-mensa-menu/index.ts` — **erste Edge Function in diesem Projekt** (Deno, `deno_dom` für echtes HTML-Parsing). Begründung gegen eine reine PL/pgSQL-Lösung: der Cookie/CSRF-Zwei-Schritt (Set-Cookie aus Antwort 1 → Cookie-Header in Anfrage 2) plus echtes HTML-Parsing ist mit `pg_net` (async/fire-and-forget, kein DOM-Parser in Postgres verfügbar) unpraktikabel; eine Deno Edge Function macht beides mit Bordmitteln (`fetch`, `Headers.getSetCookie()`, `DOMParser`).

- **Ablauf**: GET (Cookies + CSRF-Token einsammeln) → POST mit allen 4 `location_ids` in einem Request → `querySelectorAll('.card.mt-3')`, pro Block `h5`-Text gegen Mensa-Namen matchen (`/harzmensa/i` usw.) → `querySelectorAll('.food-container')` innerhalb des Blocks → je Karte Name/Preise/Badges/Zusatzstoffe parsen → bei **0 geparsten Gerichten oder fehlendem CSRF-Token wird NICHT geschrieben** (verhindert, dass eine Struktur-/Session-Änderung der Fremdseite den bestehenden Speiseplan stillschweigend leert; der alte Stand bleibt stehen, der Client erkennt ihn über den `date`-Filter selbst als veraltet).
- **Schreiben**: `POST .../rest/v1/rpc/replace_mensa_menu` mit `SUPABASE_SERVICE_ROLE_KEY` (automatisch in der Function-Umgebung verfügbar) als Bearer-Token.
- **Trigger**: `pg_cron` + `pg_net` (Migration `20260911000030_mensa_scrape_cron.sql`, `net.http_post` gegen die Function-URL) — offizielles Supabase-Pattern für „Scheduled Edge Functions". `pg_net` wird durch dieses Feature **erstmals** in diesem Projekt aktiviert (`20260911000020_pg_net_extension.sql`, bewusst als eigene, extra gegenzulesende Migration — neue Capability-Klasse: Postgres kann damit beliebige ausgehende HTTP-Requests machen, anders als die sonst rein additiven Schema-Migrationen dieses Projekts).
- **Zeitpunkt `10 3 * * *` (UTC)**: die 4-Uhr-Berlin-Tagesgrenze liegt winters bei 3:00 UTC, sommers bei 2:00 UTC — 3:10 UTC liegt in beiden Fällen sicher danach (gleiches DST-Argument wie bei `prune-cron-job-run-details`/`daily-winners`).
- **Auth-Header via Vault**: der Cron-Job liest den Service-Role-Key für den Function-Aufruf aus Supabase Vault (`vault.decrypted_secrets`, Secret-Name `mensa_scrape_trigger_key`) statt ihn im Klartext in einer committeten Migration zu speichern — das Secret selbst wird einmalig manuell angelegt (`select vault.create_secret(...)`, nie als `.sql`-Datei im Repo).
- **Housekeeping**: `pg_net` protokolliert jede Antwort in `net._http_response`, analoges Wachstumsrisiko wie `cron.job_run_details` (siehe CLAUDE.md „Datenbank-Größe") — nach dem Rollout beobachten, bei Bedarf einen Prune-Cron nach dem `prune-cron-job-run-details`-Muster ergänzen.

### Datenmodell

- **`mensa_menu_items`** (Migration `20260911000010_mensa_menu.sql`): `mensa_key, date, dish_name, price_student, price_staff, price_guest, badges (text[]), allergen_codes (text[]), sort_order, scraped_at`. **Voller Delete+Insert-Replace pro Scrape-Lauf statt Historie** (`replace_mensa_menu(p_date, p_items)`, `SECURITY DEFINER`) — die Tabelle bildet immer nur „heute" ab, kein unbeaufsichtigtes Wachstum über die Zeit. Client liest direkt per `GET .../rest/v1/mensa_menu_items?date=eq.<todayKey()>` (kein RPC nötig, gleiches Muster wie `race_checkpoint_claims`); der `date`-Filter ist zugleich Sicherheitsnetz — schlägt ein Scrape fehl, zeigt der Client „heute kein Plan verfügbar" statt eines veralteten Standes.
- **Schreibschutz**: kein `INSERT`/`UPDATE`/`DELETE`-Grant für `anon`/`authenticated` auf die Tabelle selbst. `replace_mensa_menu()` prüft `auth.role() = 'service_role'` explizit im Funktionskörper und wirft sonst `RAISE EXCEPTION` — nötig, weil (anders als z. B. `claim_streak_milestone()`) kein natürlicher `auth.uid()`-Filter existiert, der einen Fremdzugriff harmlos machen würde (die Funktion schreibt unconditional für alle Mensen), und `REVOKE EXECUTE ... FROM PUBLIC` in diesem Projekt nachweislich wirkungslos ist (siehe unten).
- **Gluten-Markierung**: `allergen_codes` enthält die rohen Zusatzstoff-/Allergen-Codes aus der Fremdseite (z. B. `{'2','A1','A3','G2'}`). Codes ab Buchstabe „A" kennzeichnen glutenhaltiges Getreide (A1 Weizen-, A2 Roggen-, A3 Gersten-, A4 Hafergluten, …) — der Client markiert entsprechende Gerichte rot (`.mc-dish-gluten`, `dishHasGluten()` prüft `/^A\d*$/i` gegen jeden Code). Prüfung läuft rein client-seitig gegen das gespeicherte Array, keine erneute Textanalyse im Browser nötig.

### Check-in / Voting

- **Datenmodell**: `profiles.mensa_checkin` (`'harzmensa'|'franckesche'|'neuwerk'|'tulpe'|'zuhause'|NULL`, CHECK-Constraint) + `profiles.mensa_checkin_date` — exaktes Gegenstück zu `library_checkin`/`library_checkin_date`. **Kein Reset-Cron**, `get_mensa_checkins()` filtert serverseitig auf `mensa_checkin_date = heute (Berlin, 4-Uhr-Grenze)`; Client filtert beim Login identisch (`userMensaCheckin` nur übernommen, wenn `profile.mensa_checkin_date === todayKey()`).
- **`'neuwerk'` als Wert** kollidiert namentlich mit dem `LIBRARY_BUILDINGS`-Key gleichen Namens (Bibliotheks-Check-in) — komplett getrenntes Feld (`mensa_checkin` vs. `library_checkin`), nur ein Namens-Zufall (Mensa Neuwerk ≠ Bibliothek Neuwerk).
- **`get_mensa_checkins()` RPC** (`SECURITY DEFINER`): identisches Scoping wie `get_library_checkins()` (`public = true AND clan_id = my_clan_id()`). Schreib-Pfad ist reines `PATCH` über den bestehenden generischen `saveEggProfile()`-Helper (kein RPC nötig).
- **Klick-Toggle**: `setMensaCheckin(key)` — Kopie von `setLibraryCheckin()`s Toggle-Logik (Klick auf die aktuell gewählte Mensa hebt den Check-in auf, Klick auf eine andere verschiebt ihn dorthin). Optimistisches lokales Update (`userMensaCheckin`/`mensaCheckins`) + sofortiges Re-Render, danach fire-and-forget `saveEggProfile()`.
- **Anzeige**: pro Mensa-Kachel ein Icon (Avatar oder 👤-Platzhalter) pro eingecheckter Person (`.mc-checkin-icon`, gruppiert wie `libGroups` beim Bibliotheks-Check-in) + eine Gesamtstimmenzahl (`.mc-checkin-count`). „Zu Hause" ist eine 5. Option ohne Speiseplan, nur Check-in.
- **Event-Delegation**: ein `click`-Listener wird in `initLeaderboard()` auf den persistenten `#mensa-content`-Knoten gebunden (nicht auf Kind-Elemente), da `renderMensaCard()` bei jedem Aufruf `wrap.innerHTML` komplett neu baut — gleiches Muster wie beim `#lb-racetrack`-Knoten.
- **Load/Poll**: `loadMensaCard()` (Menü + Check-ins zusammen, einmal beim Login/`initLeaderboard()`) lädt einmalig den Speiseplan und die Check-ins. Im bestehenden 60s-Poll der Ranglisten-/Rennstrecken-Kachel wird zusätzlich `loadMensaCheckins()` (ohne erneuten Menü-Fetch, der Speiseplan ändert sich untertags nicht) aufgerufen — kein eigener Intervall nötig, läuft im bestehenden Rhythmus/Gating mit.

### Bekannte Einschränkungen

- **Robustheit gegen Struktur-Änderungen der Fremdseite**: der Scrape ist ein reverse-engineertes, undokumentiertes Verhalten von `meine-mensa.de` — ändert sich CSS-Klassenname, CSRF-Flow oder CORS-Policy dort, kann der tägliche Scrape stillschweigend fehlschlagen (Function gibt dann `500` zurück, loggt den Fehler, schreibt nichts). Es gibt **keinen automatischen Retry** — ein fehlgeschlagener Tag bleibt bis zum nächsten planmäßigen Cron-Lauf (nächster Tag) auf dem letzten Stand stehen, den der `date`-Filter im Client dann korrekt als „nicht verfügbar" zeigt.
- **`REVOKE EXECUTE ... FROM anon` ist in diesem Projekt wirkungslos** (siehe „Rennstrecke" → Diamanten-Checkpoints, gleiche verifizierte Einschränkung) — `replace_mensa_menu()` sichert sich deshalb über einen expliziten `auth.role()`-Guard im Funktionskörper statt über GRANT/REVOKE ab.
- Kein Bild-Hotlinking auf `meine-mensa.de`-Assets (Gerichtefotos) — nur Text (Name, Preise, Badges als Text-Labels) wird übernommen.
